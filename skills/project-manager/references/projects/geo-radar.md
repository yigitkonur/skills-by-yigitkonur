# Project: geo-radar (Project Radar)

Domain notes for supervising work in `/root/dev/geo-radar`. Distilled from a long
supervision campaign over a plan/spec alignment effort. Verify against current code before
asserting any of this as fact — it is a point-in-time record, not live state.

Live surface: `https://project-radar.vercel.app`

---

## 1. What the campaign was about

A frontend that shipped ahead of its backend, plus a set of planning documents meant to
describe how the two would meet. The supervision goal was **plan/spec alignment** —
making the frontend plan, the backend contract, and the shipped code describe the same
system — with deployment explicitly *not* in scope for most of it.

That scope correction happened mid-campaign: the assistant framed the goal as "ship a demo,
deploy it"; the user corrected that the real target was perfecting the three-way alignment.
The right response was a one-line acknowledgement and a re-issued mission, not a defence.

**Keep the scope boundary restated in every mission**, or the worker wanders:

```
scope     = plans/specs only
forbidden = app code edits, push, deploy, new features
```

## 2. Layout facts worth knowing

- Frontend assets live under `assets/` as plain JS/CSS modules loaded by `index.html`
- A `design-system/` directory exists and was at one point untracked by git — meaning a
  fresh clone would not have it. Existence checks against `git ls-files` catch this class
- The renderer ownership map is a known trap: a plan claimed `assets/overview.js` owned the
  Overview page, but that file **did not exist** — `renderOverviewPage` lives in
  `assets/dashboards.js`, and `assets/overview.css` is styling only

That last one is the archetype for this project: **the agent's own verification script
validated markdown links and passed, while the code paths it blessed didn't exist.** Always
run existence checks on claimed paths and symbols, not just document internals.

## 3. Confirmed defects found by real browser testing

Static analysis suspected all three; only a live browser proved them:

- **Language toggle** wrote `localStorage` but never read it back, and the control was
  hidden behind a flag — so the preference silently did nothing
- **"Live Stream Active" feed** in Agent Analytics was generated by
  `setInterval + Math.random()` — fabricated data presented as live
- **Mobile overflow** — a 375px viewport produced a 395px page on one tab

The lesson encoded in `verification.md` §8 comes from here: if behaviour is observable,
observe it. Serve the exact commit (`git archive <sha> | tar -x -C /tmp/snap`) rather than
the dirty working tree, then drive a real browser one command at a time.

## 4. Contract-parity trap

The plan documents achieved **exact name parity** across 36 commands, 13 resources, and 23
error codes — and were still unimplementable, because:

- payload and result shapes carried `unknown` placeholders instead of field-level types
- nullability and ordering were undefined
- error codes had no `retryable` / retry-strategy / idempotency-key semantics
- resources had no backend fulfillment path or authorization predicate
- invalidation targets didn't cover every resource a mutation actually affected

**Name parity is necessary but nowhere near sufficient.** When a worker claims "N commands
in exact parity", extract all sets yourself, diff them, *and then* check the semantics
above.

## 5. Blockers that independent reviewers surfaced

The worker reported "VERDICT PASS all final verification checks". Independent adversarial
reviewers overturned it three separate times, finding:

- **Impossible phase order** — a phase consuming its own input from a later phase
- **Unreachable onboarding** — the only path to the invite-acceptance screen ran through a
  suspended account
- **Unusable read-privilege model**
- **Suspension bypass** via invite acceptance
- **Refund double-spend paths** — the same idempotency key accepted in two different states

None were visible from the worker's own green checkmarks. This is the strongest argument in
the whole skill for spawning reviewers whose explicit job is to *refute*.

## 6. Product decisions that resolved ambiguity

When operating autonomously, these were decided and stated explicitly rather than asked:

1. Prompt Volumes remains a launch surface → gets a dedicated safe resource
2. Brand Hub is canonical; the shadowed legacy controller is retirement debt
3. Fake outward-effect forms may not claim submission succeeded without a real integration

Each anchors to a principle the user had already stated: **don't lie to the user, don't fake
external effects, don't present demo data as live.** That principle resolves most product
ambiguity in this project without needing to ask.

## 7. Worker failure modes observed here

Ranked by cost, from a forensic pass over a nine-hour session:

1. **Wrote exhaustive plans instead of the code the plans described** — named seven
   implementation files in its own plan and wrote zero of them. Commit ratio was
   **0 CODE : 8 DOCS : 2 CHORE**
2. **Over-used subagents for work it then redid itself** — launched eleven audit agents,
   manually re-verified nearly every finding; two died in a bash-isolation loop
3. **Got stuck on git/worktree plumbing** — branched from stale `origin/main` twice, and
   stranded nine background agents' cwd by switching into a worktree mid-flight
4. **Delegated the definition of done to a hypothetical future agent**
5. **Green checkmarks that checked the wrong thing** (the owner-map case above)
6. **Scope creep during remediation** — given ten blockers, rewrote adjacent architecture
   and left the diff dirty for hours

Counters for each are in `verification.md` §13 and the escape-hatch phrasebook in
`report-templates.md` §9.

## 8. What worked

- **The wave discipline** — six waves, blocker count shrinking 20 → 10 → 7 → 3 → 1 → PASS
- **The A-or-B checkpoint** — converted an endless edit loop into a concrete blocker list
  within one turn
- **The supervisor addendum** — appending your own independently-found evidence rather than
  rewriting the mission
- **Post-compact re-anchoring** — without it, the worker restarted the entire audit from
  scratch and would have discarded hours of pending work
