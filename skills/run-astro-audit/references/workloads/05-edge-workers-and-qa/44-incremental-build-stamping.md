# Mission Brief: Incremental Build Stamping & Recipe Verification Audit

## 3.0 Skills / Tools: view_file, run_command.

## 3.1 Context Block

To avoid rebuilding unchanged pages across 3,900+ routes, The application implements incremental build stamping:

- `scripts/release/astro/stamp-build-identity.mjs`
- `scripts/release/astro/prove-incremental-recipes.mjs`
- Hash trees of content collections, component sources, and configurations are stored in build manifests.
- Architecture Rule: Production preview purity over dev caching. Cache stamps must exclusively validate production-grade artifacts (`dist/`), never caching unminified Vite dev outputs, dev toolbars, or HMR modules.
- Scoped Styling Invariant: Astro compiles `<style>` blocks into static CSS scoped with `data-astro-cid-[hash]`. Because component styles affect rendered markup and CSS bundles, any modification to a component's scoped `<style>` block must invalidate that component's build recipe hash even if frontmatter and markdown body are unchanged.
- Global Styles Isolation: Root stylesheets (`src/styles/globals.css`, `@import "tailwindcss"`) must trigger global shard invalidation, whereas changes to child components using `:global()` nested inside a scoped selector must strictly invalidate only routes consuming that component.
- Schema Typing Sync: Stamping algorithms must incorporate `.astro/types.d.ts` generated by `astro sync` to detect changes in Content Layer collection schemas.

### Concrete Bad vs. Best Practice Architectural Patterns

#### Pattern 1: Shallow Stamping vs. Deep Dependency Recipe Hashing (RULE-ID: 10-auditing-testing-and-nextjs-migration/06-enforce-astro-check-quality-gate-in-ci)

##### ❌ Bad Practice / Anti-Pattern

```javascript
// scripts/release/astro/stamp-build-identity.mjs - Shallow stamping anti-pattern
// BAD: Hashing git HEAD or raw markdown only; misses component scoped CSS & Astro schema changes!
export function computeShardStamp(collectionName) {
  const commit = execSync('git rev-parse HEAD').toString().trim()
  const mtime = fs.statSync(`src/content/${collectionName}`).mtimeMs
  return crypto.createHash('sha256').update(`${commit}-${mtime}`).digest('hex')
}
```

_Why this fails:_ If a developer edits a component's `<style>` tag, tweaks Tailwind utility classes, or alters content schema fields, git revs or raw collection timestamps may remain unchanged, resulting in stale cache hits that emit broken HTML or misaligned styles into production.

##### ✅ Best Practice / Idiomatic

```javascript
// scripts/release/astro/stamp-build-identity.mjs - Deep dependency recipe hashing
import crypto from 'node:crypto'
import fs from 'node:fs'

export function computeRecipeHash(routeEntry, componentTree, configPaths) {
  const hasher = crypto.createHash('sha256')
  // Hash route template, all imported .astro components (including scoped <style>), and configs
  hasher.update(fs.readFileSync(routeEntry))
  for (const compPath of componentTree) {
    if (fs.existsSync(compPath)) hasher.update(fs.readFileSync(compPath))
  }
  // Include global Tailwind v4 entry, Astro configs, and generated type definitions
  for (const cfg of configPaths) {
    if (fs.existsSync(cfg)) hasher.update(fs.readFileSync(cfg))
  }
  return hasher.digest('hex')
}
```

#### Pattern 2: Exposing Build Secrets via PUBLIC_ Prefixes (RULE-ID: 06-middleware-and-auth/11-server-secrets-astro-env)

##### ❌ Bad Practice / Anti-Pattern

```typescript
// scripts/release/astro/build-manifest.ts - Unsafe secret handling in build artifacts
// BAD: Exposing server credentials to client bundle and build manifests via PUBLIC_ prefix
export const buildMeta = {
  buildTime: Date.now(),
  deploySecret: import.meta.env.PUBLIC_DEPLOY_KEY, // CRITICAL: Exposes secret to browser!
}
```

_Why this fails:_ Prefixing environment variables with `PUBLIC_` bakes private tokens into client-side JavaScript bundles, search indexes, and static cache manifests.

##### ✅ Best Practice / Idiomatic

```typescript
// astro.config.mjs & src/worker.ts - Type-safe server environment boundary
import { defineConfig, envField } from 'astro/config'

export default defineConfig({
  env: {
    schema: {
      DEPLOY_KEY: envField.string({ context: 'server', access: 'secret' }),
    },
    validateSecrets: true,
  },
})

// Access strictly on the server:
import { DEPLOY_KEY } from 'astro:env/server'
```

#### Pattern 3: Skipping astro check in Build Pipelines (RULE-ID: 10-auditing-testing-and-nextjs-migration/06-enforce-astro-check-quality-gate-in-ci)

##### ❌ Bad Practice / Anti-Pattern

```json
// package.json - Anti-Pattern: tsc ignores .astro components, leaving broken stamps
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "node scripts/release/astro/stamp-build-identity.mjs && astro build"
  }
}
```

_Why this fails:_ `tsc --noEmit` ignores `.astro` component files completely. Type mismatches, invalid props, or altered Content Layer schema definitions pass undetected, causing runtime rendering failures in statically stamped routes.

##### ✅ Best Practice / Idiomatic

```json
// package.json - Idiomatic: Enforce astro check with strict failing severity before stamping
{
  "scripts": {
    "typecheck": "astro check --minimumFailingSeverity error",
    "build": "astro sync && astro check --minimumFailingSeverity error && node scripts/release/astro/stamp-build-identity.mjs && astro build"
  }
}
```
