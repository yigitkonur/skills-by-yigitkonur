# Widgets to Views: Complete Rewrite

*Read this to migrate MCP App widgets (v1) to Views (v2).*

In `mcp-use v1`, UI components were called "widgets" and stored under `resources/<name>/widget.tsx`. They used the `useWidget` hook, returned ad-hoc `props` hidden from the model, and wrapped UI inside the aggregate `McpUseProvider`.

In `mcp-use v2`, widgets are completely rewritten as **Views**: modular React components located at `views/<name>/view.tsx`. Views bind declaratively to tools via `view: { name }`, access typed inputs and outputs via `useToolContext<"tool-name">()`, cleanly separate model-visible state (`useViewState`) from ephemeral component state (React `useState`), and advertise host rendering metadata via `ViewConfig`.

---

## At a Glance: Widgets to Views Diff

| Surface / Concept | Legacy v1 Widgets (`mcp-use <= 1.34.5`) | Canonical v2 Views (`mcp-use >= 2.8.2`) | Impact / Action |
|---|---|---|---|
| **Folder Location** | `resources/<name>/widget.tsx` | `views/<name>/view.tsx` | Move component files to `views/` directory |
| **Tool Property** | `widget: { name: "...", invoking: "..." }` | `view: { name: "...", csp?: {...} }` | Rename property; remove `invoking`/`invoked` strings |
| **Output Schema** | Optional | **Mandatory** (`outputSchema: z.object(...)`) | Required for all tools that declare a `view` |
| **Result Function** | `return widget({ props, output });` | Raw `{ content: [...], structuredContent, _meta }` | `structuredContent` sent to model & view; `_meta` view-only |
| **Primary Hook** | `useWidget<{ props }>()` | `useToolContext<"tool-name">()` | Typed by tool name; provides `status`, `toolInput`, `toolOutput`, `meta` |
| **View State Hook** | `useWidgetState<T>()` | `useViewState<T>()` | **Root state must be a JSON object**, not a bare primitive |
| **Theme Hook** | `useWidgetTheme()` | `useViewTheme()` | Returns `{ theme: "light" \| "dark" }` |
| **Root Provider** | `<McpUseProvider autoSize>` | Framework-owned bootstrap; optional `<ThemeProvider>` / `<AppsSDKUIProvider>` | Remove aggregate `<McpUseProvider>` wrapper |
| **Model Context** | Untyped text in `output` | `<ModelContext content="...">` or `useModelContext()` | Expose dynamic view state/evidence to model context |
| **Sibling Tool Calls**| `const { callTool } = useWidget()` | `const tool = useCallTool("sibling-tool")` | Hook exported from `mcp-use/react`; typed via `mcp-env.d.ts` |
| **Static Assets** | `/_mcp-use/widget/<name>/asset.png` | `public/` directory resolved with `getPublicBaseUrl()` | Place static files in root `public/` folder |
| **Wire MIME Type** | `text/html+skybridge` / `ui://widget/` | `text/html;profile=mcp-app` / `ui://views/` | Auto-generated by Vite bundler |

## File Layout and Directory Structure

### Legacy v1 Layout:
```
my-app-server/
├── index.ts
├── resources/
│   ├── product-search/
│   │   └── widget.tsx           # Legacy React component
│   └── results-table/
│       └── widget.tsx
```

### Canonical v2 Layout:
```
my-app-server/
├── index.ts                     # MCPServer initialization & tool exports
├── views/
│   ├── product-search/
│   │   └── view.tsx             # React component + viewConfig export
│   └── results-table/
│       └── view.tsx
├── public/                      # Static assets (images, icons, svgs)
├── .mcp-use/build/              # Generated Vite build artifacts
└── package.json
```

**Key rules**:
- One View per directory directly under `views/` (nested subdirectories like `views/admin/users/view.tsx` are ignored).
- Component filename must be `view.tsx`.

## Tool Binding: `widget` → `view` & `outputSchema`

### Before (v1):
```typescript
server.tool({
  name: "search",
  schema: z.object({ query: z.string() }),
  widget: { name: "product-search", invoking: "Searching...", invoked: "Results ready" },
  cb: async ({ query }) => widget({ props: { query, results: [...] }, output: text(...) }),
});
```

### After (v2):
```typescript
export const search = server.tool(
  {
    name: "search",
    title: "Search Products",
    description: "Search catalog and render interactive result cards",
    inputSchema: z.object({ query: z.string() }),
    outputSchema: z.object({
      query: z.string(),
      count: z.number(),
    }),
    view: {
      name: "product-search",           // Matches views/product-search/view.tsx
      description: "Interactive product search results",
      csp: {
        connectDomains: ["https://api.example.com"],
        resourceDomains: ["https://cdn.example.com"],
      },
      permissions: { camera: {} },      // Named capabilities object, not string array
    },
  },
  async ({ query }) => {
    const results = await searchProducts(query);
    return {
      content: [{ type: "text", text: `Found ${results.length} products matching "${query}"` }],
      structuredContent: { query, count: results.length }, // Model-visible, schema-checked
      _meta: { results },                                   // View-only data (hidden from model)
    };
  }
);
```

### Critical Difference: `structuredContent` vs. `_meta`
- In v1, `widget({ props })` kept `props` hidden from the model.
- In v2, **`structuredContent` is validated against `outputSchema` and sent to both the model and the View**.
- To keep large, verbose, or private View data out of the model's prompt context, place it in **`_meta: { ... }`** and access it via `useToolContext().meta`.

## View Component Migration: Hooks and Providers

### Before: Legacy v1 `widget.tsx`
```tsx
import { useWidget, useWidgetState, useWidgetTheme, McpUseProvider } from "mcp-use/react";
import React from "react";

export default function SearchWidget() {
  const { props, isPending } = useWidget<{ query: string; results: any[] }>();
  const [expanded, setExpanded] = useWidgetState<boolean>(false);
  const { theme } = useWidgetTheme();

  if (isPending) return <p>Loading...</p>;

  return (
    <McpUseProvider autoSize>
      <div style={{ color: theme.textColor }}>
        <button onClick={() => setExpanded(!expanded)}>Toggle</button>
        <ul>
          {props?.results?.map((r) => (
            <li key={r.id}>{r.name}</li>
          ))}
        </ul>
      </div>
    </McpUseProvider>
  );
}
```

---

### After: Canonical v2 `views/product-search/view.tsx`
```tsx
import React, { useState } from "react";
import {
  useToolContext,
  useViewState,
  useCallTool,
  useViewTheme,
  ThemeProvider,
  ModelContext,
} from "mcp-use/react";
import type { ViewConfig } from "mcp-use/react";

type SearchMeta = {
  results: Array<{ id: string; name: string }>;
};

// Export view display modes and capabilities
export const viewConfig: ViewConfig = {
  displayModes: ["inline", "fullscreen"],
  autoResize: true,
};

export default function SearchView() {
  const ctx = useToolContext<"search">();
  const { theme } = useViewTheme();

  // Model-Visible State: Root MUST be a JSON object, not a bare boolean/string!
  const [viewState, setViewState] = useViewState<{ expanded: boolean }>({
    expanded: false,
  });

  // Ephemeral State: Local to this React component; model does not see this
  const [hoveredId, setHoveredId] = useState<string | null>(null);

  // Companion Tool Hook
  const detailsTool = useCallTool("get-product-details");

  if (ctx.status === "pending") {
    return <ThemeProvider><p className="p-4 text-sm text-gray-500">Loading search results…</p></ThemeProvider>;
  }

  if (ctx.status === "error") {
    return <ThemeProvider><p className="p-4 text-sm text-red-500">Error: {ctx.error.message}</p></ThemeProvider>;
  }

  // Schema-checked output visible to model and view
  const { query, count } = ctx.toolOutput;

  // View-only metadata hidden from model prompt
  const results = (ctx.meta as SearchMeta | undefined)?.results ?? [];

  const handleSelect = async (id: string) => {
    await detailsTool.callTool({ productId: id });
  };

  return (
    <ThemeProvider>
      {/* Exposes dynamic UI state to the model conversation turn */}
      <ModelContext content={`View expanded: ${viewState.expanded}. User hovering: ${hoveredId ?? "none"}`}>
        <div className="p-4 max-w-lg">
          <div className="flex items-center justify-between mb-3">
            <h3 className="font-semibold text-base">Results for "{query}" ({count})</h3>
            <button
              className="text-xs px-2 py-1 border rounded"
              onClick={() => setViewState({ expanded: !viewState.expanded })}
            >
              {viewState.expanded ? "Collapse" : "Expand"}
            </button>
          </div>

          <ul className="space-y-1">
            {results.map((r) => (
              <li
                key={r.id}
                onMouseEnter={() => setHoveredId(r.id)}
                onMouseLeave={() => setHoveredId(null)}
                onClick={() => handleSelect(r.id)}
                className="p-2 border rounded cursor-pointer hover:bg-gray-50 dark:hover:bg-gray-800"
              >
                {r.name}
              </li>
            ))}
          </ul>
        </div>
      </ModelContext>
    </ThemeProvider>
  );
}
```

## State Architecture: Model-Visible vs. Ephemeral State

In v1, `useWidgetState` blurred the line between UI state and model context. In v2, state concerns are explicitly split:

| State Concern | Canonical Mechanism | Visibility & Lifecycle |
|---|---|---|
| **Model-Visible State** | `useViewState<T>({ ... })` | Serialized and transmitted to host model on mutation; persists across host re-renders. **Root state must be a JSON object.** |
| **Ephemeral UI State** | React `useState()` | Stays strictly inside iframe memory (hover, form input typing, animations). Model never sees it. |
| **Conversational Context** | `<ModelContext content="...">` | Appends a descriptive text summary of the current UI state to the model turn. |
| **Evidence Attachments** | `useModelContext().add("key", block)` | Attaches structured evidence (`text`, `image`) to the next user turn in ChatGPT. |

> **Hard Constraint**: `useViewState` throws a runtime error if passed a bare primitive (`useViewState(false)` or `useViewState("active")`). Always use an object: `useViewState({ active: true })`. Furthermore, keys beginning with `_uiContext` are reserved for host window layout metadata and must not be used.

## Sibling Tool Invocations from Views

Views can invoke registered MCP tools directly over the host postMessage bridge:

```tsx
import { useCallTool, useDynamicTool } from "mcp-use/react";

// 1. Static Typed Tool Call (tool registered with exported ToolRef)
// Tool name is passed as a string; types are derived from mcp-env.d.ts
const details = useCallTool("get-details");
const handleInspect = async () => {
  const result = await details.callTool({ recordId: "rec_123" });
};

// 2. Dynamic Tool Call (for tools registered dynamically from OpenAPI or loops)
const dynamic = useDynamicTool<{ id: string }, { success: boolean }>("dynamic-action");
const handleDynamic = async () => {
  const res = await dynamic.callTool({ id: "rec_123" });
};
```

> **Warning**: Never import server tool definitions directly into View components (`import { myTool } from "../../server.js"`). Views are bundled as browser-side code by Vite; importing server files leaks Node dependencies and breaks the build.

## Declarative Content Security Policy (CSP) & Permissions

v2 manages iframe security declaratively on the tool's `view.csp` property:

```typescript
export const mapTool = server.tool(
  {
    name: "show-map",
    inputSchema: z.object({ location: z.string() }),
    outputSchema: z.object({ coordinates: z.array(z.number()) }),
    view: {
      name: "map-view",
      csp: {
        connectDomains: ["https://api.mapbox.com"],
        resourceDomains: ["https://cdn.mapbox.com"],
        frameDomains: ["https://embed.mapbox.com"],
        baseUriDomains: ["https://example.com"],
      },
      // permissions requests browser capabilities from the host
      permissions: {
        geolocation: {},
        clipboardWrite: {},
      },
    },
  },
  async ({ location }) => ({ content: [...], structuredContent: { coordinates: [0, 0] } })
);
```

## Handling Cached Legacy ChatGPT Widget URIs

In v1, widgets were advertised under URI `ui://widget/<name>.html`. In v2, Views are served at `ui://views/<name>.html`. A published ChatGPT app caches the legacy URI in tool metadata. To prevent 404s when deploying v2, install temporary rewrite middleware:

```typescript
// Rewrite ui://widget/<name>.html to ui://views/<name>.html for legacy ChatGPT clients
server.use(server.basePath, async (c, next) => {
  if (c.req.method !== "POST") return next();
  const body = await c.req.raw.clone().json().catch(() => undefined);
  const legacyUri = body?.method === "resources/read" ? body.params?.uri : undefined;
  if (typeof legacyUri === "string" && legacyUri.startsWith("ui://widget/")) {
    const viewName = legacyUri.slice("ui://widget/".length).replace(/\.[^.]*\.html$/, ".html");
    const rewrittenUri = `ui://views/${viewName}`;
    const headers = new Headers(c.req.raw.headers);
    headers.delete("content-length");
    c.req.raw = new Request(c.req.raw, {
      body: JSON.stringify({ ...body, params: { ...body.params, uri: rewrittenUri } }),
      headers,
    });
  }
  await next();
});
```

## Anti-Patterns and Common Traps

| Anti-Pattern | Root Mechanism & Failure Mode | Canonical v2 Fix |
|---|---|---|
| **Importing from `@mcp-use/react`** | The scoped package does not exist on npm. Fails at build time: `Cannot find module '@mcp-use/react'`. | Import from the subpath of root: `import { useToolContext } from "mcp-use/react";`. |
| **Passing Bare Primitive to `useViewState`** | `useViewState(false)` or `useViewState("id")` violates host JSON dictionary protocol. | Pass an object dictionary: `useViewState({ expanded: false })`. |
| **Writing to `_uiContext` in View State** | `_uiContext` is a reserved system key for window dimensions and layout mode. | Use custom property names for application state. |
| **Importing Server Modules into `view.tsx`** | Writing `import { search } from "../../index.js"` drags Node.js server dependencies into the client Vite bundle. | Pass tool names as strings (`useCallTool("search")`); types derive from `mcp-env.d.ts`. |
| **Omitting `outputSchema` on UI Tools** | Tools declaring a `view` without `outputSchema` cannot validate `toolOutput` and fail type generation. | Define and assign `outputSchema` on every UI-bound tool. |
| **Expecting `props` in `useToolContext`** | v1 `props` is replaced by `toolOutput` (model-visible) and `meta` (view-only). | Read `ctx.toolOutput` for schema data and `ctx.meta` for View-only data. |
